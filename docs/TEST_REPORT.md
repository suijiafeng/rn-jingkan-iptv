## 2026-10-18 · 万级频道列表性能（分支 perf/large-list，基于 96087d3）

方法：模拟器 Medium_Phone（arm64，软件渲染），release APK（debug 测试签名，原位升级保留已导入的 iptv-org index.m3u 共 11,344 个频道）。改动前后各打一个带临时 logcat 计时标记的包（`[perf]` 日志只用于测量，未提交），用 logcat 时间戳和设备端 `date` 计时，不用界面导出轮询；滚动用 `dumpsys gfxinfo` 记录 30 次连续上滑。模拟器 GPU 帧耗 p50 一直是 18 ms，滚动指标只作相对参考，不代表 S25 Ultra。

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| 切到“频道”页（11,344 行）到列表可见 | 读取 275–613 ms + 提交 18–75 ms（3 次） | 首屏 40 行 39–92 ms + 提交 16–73 ms；其余行后台补齐，总计 288–416 ms |
| “频道”页点收藏 | 点击到整表重读完成 458–1005 ms，每次重读 11,344 行 | 点击到星标更新帧 57–65 ms（首次 190 ms），不再重读频道表，只重读来源计数 |
| 选台面板搜索（Node，11,344 个频道，逐字输入 n/ne/new/news） | 每次 8–14 ms | 首次打开建索引 9 ms，之后每次 2–4 ms；结果与旧实现逐条一致 |
| 滚动（3 轮 × 30 次上滑，同一起点） | 卡顿帧 4.5% / 7.0% / 6.5%；p50 25–27 ms；p90 34–38 ms；p99 81–89 ms | 卡顿帧 2.1% / 5.7% / 5.1%；p50 24–25 ms；p90 31–36 ms；p99 44–89 ms |

改动：
- 列表分两次读：先读 40 行与总数（`LIMIT`/`COUNT`），再用 `OFFSET` 补齐其余行。需要恢复非零滚动位置时仍一次读完整表。头部频道数在补齐前取总数；补齐前点播放会等完整列表再建换台队列。
- 定位到首屏慢的真正原因是分组列表：`localeCompare(…, "zh-Hans-CN")` 每次比较都新建排序器，在 Hermes/Android 上单次 `listGroups` 约 110–200 ms。改为复用一个 `Intl.Collator` 后首屏读取从 129–197 ms 降到 39–92 ms（SQLite 本身：Node 中首 40 行 4 ms、整表 64 ms）。
- 收藏只在本地改这一行；收藏页（成员会变）或列表还在读取（可能读到写入前数据）时才整页重读。
- 频道行 `React.memo`，行内名称解析只算一次；行回调改为稳定引用；分隔组件不再每次渲染新建；FlatList `windowSize` 11、`maxToRenderPerBatch` 8、`removeClippedSubviews`。
- 选台面板按频道对象缓存搜索文本、分组与标题（WeakMap，行对象替换即失效）。

评估但未采用：
- 固定行高 + `getItemLayout`：行高随标签、两行名称和系统字号变化，吸顶栏和标题高度也不固定，固定高度会改变界面并在大字体下出错。
- `@shopify/flash-list`：要新增依赖并验证吸顶哨兵行；对比了三组 FlatList 设置（全部调优 / 去掉 removeClippedSubviews / 只做 memo 不调参数），卡顿帧均值 4.3% / 5.4% / 4.6%，基线 6.0%，差异接近噪声，模拟器瓶颈在软件渲染。建议在 S25 Ultra 上仍感到卡顿时再评估。
- 选台面板查询下推 SQLite：完整目录已在内存，缓存后每次过滤 2–4 ms（Node），下推反而每次按键都要过桥往返。Hermes 无 JIT，真机绝对耗时会更高，但未在设备上测（adb 点不进面板搜索框，面板会被关闭）。

## 验收建议

先安装独立测试APK并导入官方控制样本，确认首帧、声音、20秒播放；再测试真实自有来源。每项记录版本、设备系统、时间、网络和结果。遇到源错误先保留目录和收藏，重试或换台；不要把某个来源失效直接归咎于播放器，也不要将HTTP200标成可播放。
